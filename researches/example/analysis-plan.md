## Центральный исследовательский вопрос

На каких шагах воронки cart → checkout → payment → purchase после редизайна мобильного чекаута теряется наибольшее число пользователей, и есть ли сегменты с особенно выраженной просадкой конверсии?

## Подвопросы

1. На каких конкретных шагах воронки наблюдается наибольшая потеря пользователей после редизайна?
2. Есть ли пользовательские сегменты (например, новые vs. старые пользователи), где просадка выражена сильнее?
3. Можно ли связать изменения с конкретным шагом (например, paywall/платёжный шаг)?

## Гипотезы

1. После редизайна конверсия на одном из шагов (checkout или payment) снизилась значимее всего.
2. Новые пользователи теряются на этапе paywall/платёжного шага чаще, чем старые.
3. В некоторых сегментах (например, по источнику трафика) просадка выражена сильнее.

## Единица анализа

Пользовательная сессия (или пользователь в рамках сессии), проходящая через воронку cart → checkout → payment → purchase.

## Метрики

- Конверсия между шагами воронки (cart → checkout, checkout → payment, payment → purchase)
- Абсолютное и относительное изменение конверсии до/после редизайна (по is_checkout_redesign или app_version)
- Доля пользователей, выпавших на каждом шаге
- Сравнение по сегментам (новые/старые пользователи, источник трафика)

## Сегменты и разрезы

- Период: до и после редизайна (по is_checkout_redesign или app_version)
- Тип пользователя: новый / старый (по prior_purchase_count)
- Источник трафика (traffic_source)

## Необходимые данные (файлы)

### 1. data/events.csv
- **Зачем файл:** Для построения воронки и анализа переходов между шагами (cart, checkout, payment, purchase) по сегментам и периодам.
- **Зерно строки:** Одно событие пользователя (event) в приложении или на сайте.
- **Ключевые поля:**
    - user_id
    - session_id
    - event_timestamp
    - event_name (cart, checkout, payment, purchase)
    - app_version
    - is_checkout_redesign
    - traffic_source
    - cart_value (опционально для анализа чека)
    - cart_item_count (опционально для анализа состава корзины)
- **Ключ стыковки:** user_id (для join с users), session_id (для сессий)
- **Обязательность:** must-have
- **Пример SQL:**
```sql
SELECT
  user_id,
  session_id,
  event_name,
  event_timestamp,
  cart_value,
  cart_item_count,
  app_version,
  is_checkout_redesign,
  traffic_source
FROM analytics.events
WHERE event_name IN ('cart', 'checkout', 'payment', 'purchase')
  AND event_timestamp BETWEEN '2024-05-01' AND '2024-06-15'
```

### 2. data/users.csv
- **Зачем файл:** Для определения новых/старых пользователей и обогащения событийной таблицы.
- **Зерно строки:** Один пользователь.
- **Ключевые поля:**
    - user_id
    - first_seen_date
    - prior_purchase_count
- **Ключ стыковки:** user_id
- **Обязательность:** must-have
- **Пример SQL:**
```sql
SELECT
  user_id,
  MIN(event_timestamp) AS first_seen_date,
  COUNTIF(event_name = 'purchase' AND event_timestamp < '2024-05-01') AS prior_purchase_count
FROM analytics.events
GROUP BY user_id
```

## Проверки качества

- Согласованность количества пользователей/сессий между файлами
- Проверка полноты событий по каждому шагу воронки
- Проверка наличия данных по всем релевантным датам

## Ограничения

- Нет экспериментального дизайна, только описательный/сравнительный анализ
- Нет явного поля platform (невозможно сравнить с web)
- Нет device_type и registration_platform
- Возможны ограничения по детализации событий (например, если не все шаги явно логируются)
- Платформу и период до/после редизайна определяем по is_checkout_redesign или app_version (если есть однозначное соответствие)

## Что дизайн поддерживает / не поддерживает

**Поддерживает:**
- Анализ воронки cart → checkout → payment → purchase по доступным сегментам
- Сравнение до/после редизайна (по is_checkout_redesign/app_version)
- Поиск шагов и сегментов с наибольшей просадкой

**Не поддерживает:**
- Сравнение между платформами (iOS/Android/web)
- Причинно-следственный вывод о влиянии редизайна (нет A/B)
- Глубокий анализ UX без дополнительных данных

## Неразрешённые допущения

- Все ключевые события (cart, checkout, payment, purchase) корректно и полно логируются
- is_checkout_redesign или app_version позволяют корректно выделить период до/после редизайна
- prior_purchase_count корректно определяет новых/старых пользователей
