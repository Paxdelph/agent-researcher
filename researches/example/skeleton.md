# Где после редизайна мобильного чекаута теряются пользователи и можно ли объяснить это шумом

## Narrative arc

История движется от рамки данных и правил сравнения — без них любые цифры до/после ничего не доказывают — к оценке масштаба общей просадки `cart → purchase`, а затем к поиску конкретного шага воронки, который эту просадку формирует. Дальше разбор проверяет, не сосредоточена ли проблема в отдельных сегментах или объясняется изменением микса аудитории, и сопоставляет календарный контраст «до/после» с контрастом «обновившиеся против необновившихся», чтобы отделить эффект самого редизайна от самоотбора и внешнего фона. Ответ на центральный вопрос — какой шаг ломается, у кого сильнее и насколько это похоже на реальную, устойчивую проблему, а не на шум или смену микса трафика, — складывается только к финалу разбора и определяет выбор между откатом, точечным фиксом и продолжением наблюдения.

## Секции

### 1. Рамка анализа, данные и правила сравнения

- **Зачем в истории:** зафиксировать центральный вопрос, основную единицу анализа и правила, без которых наблюдаемые различия нельзя использовать для продуктового решения.
- **Вопрос / тезис:** позволяют ли доступные данные надёжно сравнить воронку до и после релиза и отделить календарное изменение от различий между пользователями с разной экспозицией к редизайну?
- **Метрики / расчёты:**
  - источник событий — `events.csv`, 2 164 строки; пользовательские признаки — `users.csv`, 400 строк;
  - основная единица анализа — пользователь в календарном окне; для каждого пользователя выбирается первая сессия с событием `cart` в соответствующем окне;
  - основная воронка строится только по событиям выбранной первой cart-сессии: шаг считается достигнутым, если соответствующее событие произошло после предыдущего шага;
  - session-level-воронка по всем cart-сессиям используется только как sensitivity check;
  - основной контраст — равные по длине календарные окна до и после подтверждённой даты релиза: 2–3 полные недели с одинаковым набором дней недели, с исключением релизного дня и периода раскатки;
  - календарные границы фиксируются до просмотра конверсий; основной расчёт выполняется в UTC, а при сверке с дашбордом отдельно проверяется сдвиг границ в Europe/Moscow;
  - `is_checkout_redesign` и `app_version` используются как маркеры экспозиции и для второго контраста, но не заменяют календарное определение pre/post;
  - второй контраст — `is_checkout_redesign = 1` против `is_checkout_redesign = 0` внутри одного пост-релизного окна, только если обе группы представлены в достаточном объёме;
  - при нескольких `cart` выбирается первое по времени событие; экспозиция, версия и `traffic_source` фиксируются по нему;
  - сессии со смешанными значениями `is_checkout_redesign` исключаются из основного exposure-контраста и возвращаются в sensitivity check с альтернативными правилами присвоения;
  - рассчитывается доля пользователей, попавших в оба календарных окна; неопределённость разницы оценивается с кластеризацией по `user_id`;
  - новый пользователь — `prior_purchase_count = 0`, вернувшийся — `prior_purchase_count > 0`, но классификация признаётся снимком без временной истории;
  - до просмотра сегментных результатов применяется объёмный gate: полноценный сегментный график строится только для ячеек с не менее чем 30 пользователями в каждом сравниваемом периоде; меньшие ячейки приводятся только как описательные значения без ранжирования;
  - до просмотра результата менеджмент должен задать минимально значимое продуктовое изменение `δ_min` для `cart → purchase` и, при необходимости, денежный порог решения; если порог не предоставлен, отчёт показывает эффект и доверительный интервал, но не объявляет изменение продуктово значимым.
- **Графики / таблицы:**
  - график не нужен: секция задаёт рамки, а не доказывает эффект;
  - основная компактная таблица сопоставимости окон:
  
    | Показатель | До релиза | После релиза | Комментарий / порог |
    |---|---:|---:|---|
    | Даты и часовой пояс | дата–дата | дата–дата | равная длина, одинаковые дни недели |
    | События в выгрузке | N | N | все четыре шага |
    | Пользователи с `cart` | N | N | знаменатель основной воронки |
    | Выбранные первые cart-сессии | N | N | одна на пользователя в окне |
    | Пользователи в обоих окнах | — | N / % | зависимые наблюдения |
    | New / returning | N / % | N / % | по `prior_purchase_count` |
  
  - отдельная диагностическая таблица качества с колонками `Проверка`, `N`, `%`, `Порог / ожидаемое правило`, `Решение для анализа`; строки: нарушения порядка событий, шаг без предшествующего шага, повторные события, смешанный redesign-флаг внутри сессии, событие раньше `first_seen_date`, несколько `traffic_source` внутри cart-сессии;
  - таблица экспозиции с колонками `Период`, `is_checkout_redesign`, `app_version`, `Пользователи с cart`, `Доля периода`; строки сортировать сначала по периоду, затем по флагу и версии.
- **Комментарий автору:**
  - таблицы сделать нативными HTML-таблицами, а не Plotly: выравнивать числа вправо, проценты показывать с одинаковой точностью, критичные проверки выделять одним акцентным цветом;
  - не использовать KPI-карточки: они скрывают знаменатели и сопоставимость окон;
  - проверить обратные аномалии воронки: `checkout`, `payment` или `purchase` без предшествующего шага, нарушенный порядок временных меток, повторные события одного типа и случаи `N purchase > N payment`;
  - квантифицировать долю пользователей, у которых событие произошло раньше `first_seen_date`. Если доля превышает 5%, обозначить `users.csv` как источник с существенной временной несогласованностью и понизить уверенность сегментации new/returning; не заменять классификацию на `first_seen_date`;
  - показать долю new/returning в каждом периоде, поскольку `prior_purchase_count` не является историческим значением на дату события и может создавать пост-трактованную классификацию;
  - проверить осмысленность `traffic_source`: рассчитать долю cart-сессий с двумя и более разными значениями источника. Если таких сессий более 10%, не интерпретировать поле как устойчивый канал привлечения и схлопнуть соответствующий анализ до ограничения данных;
  - отдельно диагностировать наличие web: распределение и паттерны `app_version`, в том числе наличие не-app-подобных значений, а также любые отличающиеся паттерны идентификаторов сессий. Если все наблюдения имеют app-подобные версии, сформулировать, что выгрузка выглядит мобильной, но отсутствие web нельзя доказать без `platform`. Если потенциальные web-события неотличимо смешаны с приложениями, указать, что группа `is_checkout_redesign = 0` может содержать web и exposure-контраст смещён;
  - отсутствие отдельного `platform` не позволяет надёжно сравнить iOS, Android и web при любом исходе диагностики;
  - флагов ботов и тестовых аккаунтов нет, поэтому такие наблюдения нельзя исключить явно.
- **Переход дальше:** после фиксации сопоставимых окон, единицы анализа и качества разбиения можно оценить масштаб общей просадки и её возможную коммерческую значимость.

### 2. Общая конверсия и масштаб возможных потерь

- **Зачем в истории:** определить, существует ли содержательный общий сигнал, достаточный для дальнейшей локализации и управленческого внимания.
- **Вопрос / тезис:** изменилась ли `cart → purchase` после релиза сильнее статистической неопределённости и заранее заданного порога продуктовой значимости, и не совпадает ли изменение со сдвигом состава корзин?
- **Метрики / расчёты:**
  - число пользователей с первой cart-сессией до и после;
  - `CR(cart → purchase) = N пользователей с последовательностью cart → purchase / N пользователей с cart`;
  - 95% доверительный интервал Wilson для каждой доли;
  - абсолютное изменение в процентных пунктах и 95% доверительный интервал разницы с кластеризацией по `user_id`;
  - относительное изменение: `(CR_after / CR_before − 1) × 100%`;
  - сопоставление абсолютного изменения с `δ_min`;
  - число дополнительных незавершённых покупок в пост-окне относительно сценария с pre-конверсией: `N_cart_after × (CR_before − CR_after)`, только если разница отрицательна;
  - ориентировочный объём `cart_value` под риском: оценённое число дополнительных незавершённых покупок × среднее значение `cart_value` среди post-cart-наблюдений; показатель маркируется как сценарный sizing, а не доказанная потеря выручки;
  - сравнение распределений `cart_value` и `cart_item_count` до/после: медиана, межквартильный размах и относительное изменение;
  - session-level-оценка общей конверсии как sensitivity check.
- **Графики / таблицы:**
  - главный визуал — горизонтальные bars от нуля для `CR(cart → purchase)`:
    - ось Y — `До релиза`, `После релиза`;
    - ось X — конверсия, %, диапазон строго от 0 до 100%;
    - error bars — 95% CI Wilson;
    - внутри или справа от каждого bar — прямая подпись `CR%; покупки / пользователи с cart`;
    - `До` — нейтральный серый, `После` — один синий акцент; легенда не нужна;
    - под графиком текстовая аннотация `Δ = … п.п.`, `95% CI […; …]`, `δ_min = … п.п.`; не кодировать `δ_min` второй осью;
  - рядом или непосредственно под графиком — точная таблица с одной строкой `cart → purchase` и колонками `До: N / denominator`, `CR до`, `После: N / denominator`, `CR после`, `Δ п.п.`, `95% CI Δ`, `Δ %`, `Дополнительные незавершённые покупки`, `cart_value под риском`;
  - состав корзин — компактная таблица со строками `cart_value` и `cart_item_count`, колонками `Медиана до`, `IQR до`, `Медиана после`, `IQR после`, `Относительное изменение`; отдельный график не строить, если таблица не указывает на заметный сдвиг.
- **Комментарий автору:**
  - bar chart обязан начинаться от нуля; не приближать ось ради визуального усиления небольшой разницы;
  - высота Plotly-визуала около 280–320 px, фон белый, вертикальная сетка минимальная, hover содержит период, числитель, знаменатель, CR и CI; `displayModeBar: false`;
  - точные значения показывать в таблице, не перегружать график относительным изменением и sizing-метриками;
  - формулировать результат как диапазон правдоподобных изменений, а не только точечную оценку. Не подставлять вместо расчёта заявленное в brief значение `−X п.п.`;
  - сценарную оценку потерь не называть фактически потерянной выручкой: она предполагает сохранение pre-конверсии и не учитывает причинность, маржу и последующие покупки;
  - если доверительный интервал включает отсутствие изменения или пересекает `δ_min`, признать решение статистически либо продуктово неопределённым.
- **Переход дальше:** если общий сигнал существует или его верхняя граница несёт существенный бизнес-риск, следующий шаг — определить, какой переход воронки формирует итоговое изменение.

### 3. Где именно теряются пользователи: декомпозиция по шагам воронки

- **Зачем в истории:** отличить локальную проблему checkout/payment от распределённого изменения всей воронки и оценить вклад каждого перехода в итоговую `cart → purchase`.
- **Вопрос / тезис:** какой переход внёс наибольший вклад в изменение общей конверсии и достаточно ли доказательств, чтобы считать его основной проблемной точкой?
- **Метрики / расчёты:**
  - `a = CR(cart → checkout)`;
  - `b = CR(checkout → payment)`;
  - `c = CR(payment → purchase)`;
  - итоговая конверсия как `CR(cart → purchase) = a × b × c`;
  - 95% Wilson CI для каждой пошаговой конверсии;
  - абсолютное и относительное изменение каждого перехода и 95% CI разницы;
  - доля выпадения на переходе: `1 − CR шага`;
  - абсолютное число выпавших пользователей на каждом переходе;
  - цепная декомпозиция общего изменения с заранее фиксированным порядком переходов:
    - вклад `cart → checkout`: `(a_after − a_before) × b_before × c_before`;
    - вклад `checkout → payment`: `a_after × (b_after − b_before) × c_before`;
    - вклад `payment → purchase`: `a_after × b_after × (c_after − c_before)`;
    - сумма вкладов должна равняться изменению итогового произведения;
  - для трёх переходов применяются одновременные интервалы или поправка Holm к проверкам различий; сегментные сравнения далее остаются исследовательскими.
- **Графики / таблицы:**
  - главный визуал — горизонтальные grouped bars пошаговой конверсии:
    - ось Y — переходы в фиксированном порядке воронки: `cart → checkout`, `checkout → payment`, `payment → purchase`; не сортировать по величине эффекта;
    - ось X — конверсия перехода, %, от 0 до 100%;
    - серии — `До релиза` и `После релиза`;
    - на каждом bar — 95% CI и прямая подпись CR;
    - в hover — числитель, знаменатель, CR, CI, доля и абсолютное число выпавших;
    - `До` — нейтральный серый, `После` — тот же синий акцент, что в секции 2;
    - справа от каждой пары — компактная аннотация `Δ … п.п.`; отрицательные значения выделять приглушённым красно-оранжевым только в аннотации, а не перекрашивать всю серию;
  - вместо двух декоративных funnel chart — диагностическая HTML-таблица с точными значениями: строки — три перехода; колонки — `Достигли шага до / знаменатель`, `CR до`, `Достигли шага после / знаменатель`, `CR после`, `Δ п.п.`, `95% CI Δ`, `скорректированный p-value / результат проверки`, `Вклад в общий Δ, п.п.`, `Доля общего изменения`;
  - строку перехода с доминирующим отрицательным вкладом выделять акцентной подложкой только при выполнении заявленных статистического и продуктового критериев.
- **Комментарий автору:**
  - не использовать классическую funnel-форму с меняющейся шириной: она затрудняет сравнение близких конверсий до/после и смешивает абсолютный размер этапа с условной конверсией перехода;
  - bars начинаются от нуля, высота около 360–420 px; минимальная сетка, прямые подписи вместо отдельной легенды при достаточном месте; `displayModeBar: false`;
  - одинаковые цвета периода должны сохраняться во всех секциях;
  - переход называется основной проблемной точкой только если его ухудшение не сводится к статистической неопределённости после учёта трёх сравнений, превышает применимый продуктовый порог и даёт доминирующий вклад в декомпозиции;
  - не выбирать шаг только потому, что у него самая низкая базовая конверсия или максимальная отрицательная точечная оценка;
  - событие `payment` — лишь прокси платёжного этапа: данных об открытии paywall, ошибках оплаты и пользовательском отказе нет.
- **Переход дальше:** локальная просадка на одном шаге и в одном типе пользователей поддерживает точечный фикс, тогда как ухудшение в нескольких переходах и сегментах требует более широкого аудита релиза и альтернативных объяснений.

### 4. Кто теряется сильнее: сегменты и микс аудитории

- **Зачем в истории:** определить, сосредоточена ли просадка среди новых пользователей или доступных источников трафика и какая часть blended-изменения объясняется сдвигом состава аудитории.
- **Вопрос / тезис:** наблюдается ли ухудшение внутри сопоставимых сегментов либо итоговая метрика изменилась преимущественно из-за роста доли сегментов с более низкой базовой конверсией?
- **Метрики / расчёты:**
  - объёмы по `период × new/returning` и, только при пригодности поля, по `период × traffic_source`;
  - доля каждого сегмента среди пользователей с `cart` до и после;
  - `CR(cart → purchase)` и конверсии соседних переходов по типу пользователя и периоду;
  - те же метрики по `traffic_source` только для источников, прошедших gate по стабильности и объёму;
  - 95% CI долей и разниц; ячейки ниже объёмного gate не визуализируются и не ранжируются;
  - прямая стандартизация отдельно для new/returning и пригодных источников:
    - эффект изменения внутри сегментов при фиксированном pre-миксе: `Σ w_before,s × (CR_after,s − CR_before,s)`;
    - эффект изменения состава: `Σ (w_after,s − w_before,s) × CR_after,s`;
    - сумма двух компонентов сопоставляется с фактическим blended-изменением;
  - разница изменений между new и returning приводится как исследовательская оценка с CI;
  - при достаточном объёме повторяется декомпозиция проблемного шага внутри new/returning, но без поиска максимума среди множества мелких групп.
- **Графики / таблицы:**
  - основной визуал — faceted horizontal grouped bars для new и returning:
    - две панели: `Новые: prior_purchase_count = 0` и `Вернувшиеся: prior_purchase_count > 0`;
    - в каждой панели ось Y содержит `cart → purchase` и, только если шаг локализован в секции 3, этот ключевой переход;
    - ось X — конверсия, %, общий диапазон 0–100% для обеих панелей;
    - серии — `До релиза` и `После релиза`, с прежней цветовой схемой;
    - error bars — 95% CI;
    - подпись у каждого значения — `CR%, N знаменателя`; справа от пары — `Δ п.п.`;
    - категории не сортировать по размеру просадки;
  - таблица стандартизации:
  
    | Компонент blended-изменения | Вклад, п.п. | Доля фактического Δ | Интерпретация |
    |---|---:|---:|---|
    | Изменение конверсии внутри сегментов | … | … | поведение при фиксированном pre-миксе |
    | Изменение состава аудитории | … | … | эффект смены долей сегментов |
    | Итого | … | 100% | сверка с фактическим blended-Δ |
  
  - при пригодном `traffic_source` — 100% stacked horizontal bars состава пользователей с `cart` до/после:
    - ось Y — период;
    - ось X — доля пользователей, 0–100%;
    - стек — значения `traffic_source`;
    - прямые подписи только для достаточно крупных долей, остальные значения доступны в hover;
    - использовать не более пяти различимых цветов; если пригодных источников больше или подписи нечитаемы, заменить график таблицей `Источник × доля до × доля после × Δ доли`, отсортированной по доле до;
  - конверсии по `traffic_source` — только HTML-таблица для прошедших gate источников: `N до`, `CR до`, `N после`, `CR после`, `Δ п.п.`, `95% CI`; не строить отдельную цветную витрину по множеству источников.
- **Комментарий автору:**
  - facet-панели должны иметь одинаковые шкалы и размеры; не использовать индивидуальный zoom для усиления различий;
  - основной график высотой около 380–440 px, без лишней сетки; hover показывает сегмент, период, числитель, знаменатель, CR и CI; `displayModeBar: false`;
  - сегментные результаты считать диагностическими, а не подтверждающими находками: не ранжировать источники по максимальной просадке и не объявлять единичную малую группу «главной проблемой»;
  - для new/returning явно напомнить, что `prior_purchase_count` является недатированным снимком; интерпретация ослабляется при противоречиях в `users.csv`;
  - если `traffic_source` часто меняется внутри сессии, снять анализ каналов и заменить его выводом о непригодности поля;
  - не использовать heatmap при двух периодах: она хуже показывает неопределённость и создаёт ложное ощущение точности.
- **Переход дальше:** после отделения внутренних изменений от микса необходимо проверить, согласуется ли сигнал именно с экспозицией к редизайну, с самоотбором обновившихся пользователей или с общим временным фоном.

### 5. Редизайн, самоотбор или совпадение: проверка альтернативных объяснений

- **Зачем в истории:** проверить, какой из трёх механизмов лучше согласуется с данными: изменение, связанное с новой версией checkout; самоотбор пользователей, обновивших приложение; либо внешний календарный фон, трафик-микс или изменение логирования.
- **Вопрос / тезис:** совпадают ли календарный и exposure-контрасты, сохраняется ли проблемный шаг во времени и сужается ли просадка по мере привыкания пользователей?
- **Метрики / расчёты:**
  - недельная динамика `CR(cart → purchase)` и конверсии перехода с наибольшим вкладом; дневная агрегация не используется из-за малого объёма;
  - число пользователей с `cart` в каждой неделе рядом с каждой оценкой;
  - изменение разрыва относительно pre-baseline по неделям после релиза:
    - последовательное приближение к pre-уровню — признак, согласующийся с привыканием или временным сбоем;
    - плоская либо усиливающаяся просадка — признак устойчивой проблемы, требующей исправления или отката;
    - при 2–3 пост-релизных точках тренд описывается осторожно и не объявляется доказанным;
  - сравнение `is_checkout_redesign = 1` и `0` внутри одного пост-релизного окна по общей и ключевой пошаговой конверсии, если обе группы проходят объёмный gate;
  - сравнение состава exposure-групп по new/returning, `traffic_source`, `cart_value` и `cart_item_count`;
  - доля пользователей, сменивших флаг или версию между окнами, и распределение `app_version` внутри каждого значения флага;
  - доли каждого `event_name` по календарным окнам и exposure-группам для диагностики изменений логирования;
  - повторный расчёт после исключения сессий с нарушенной последовательностью и смешанными флагами;
  - sensitivity check с session-level-единицей и с календарными границами в Europe/Moscow.
- **Графики / таблицы:**
  - главный визуал — два вертикально расположенных line chart в общем Plotly figure:
    - верхняя панель — недельная `CR(cart → purchase)`;
    - нижняя панель — недельная конверсия ключевого перехода из секции 3;
    - ось X — календарная неделя;
    - ось Y — конверсия, %; для каждой панели шкала фиксируется заранее и не должна визуально преувеличивать небольшое изменение, при этом нулевая база для line chart не обязательна;
    - линия соединяет недельные оценки, маркеры показывают отдельные недели, вертикальные error bars — 95% CI;
    - релизный день и исключённый период раскатки обозначаются вертикальной линией и полупрозрачной нейтральной полосой;
    - pre- и post-точки не перекрашивать как независимые серии: использовать одну линию, а границу периода показывать только релизной меткой;
    - подпись у точки — `CR%`; `N пользователей с cart` выводить второй строкой в hover и, если число точек не превышает шести, небольшой подписью под маркером;
  - таблица сопоставления двух контрастов:
  
    | Метрика | Календарный контраст: после − до | 95% CI | Exposure-контраст: redesign 1 − 0 | 95% CI | Согласованность направления |
    |---|---:|---:|---:|---:|---|
    | `cart → purchase` | … | … | … | … | да / нет / неопределённо |
    | Ключевой переход | … | … | … | … | да / нет / неопределённо |
  
  - таблица сопоставимости exposure-групп с колонками `Признак`, `redesign = 0`, `redesign = 1`, `Разница`; строки — доля new/returning, пригодные значения `traffic_source`, медиана и IQR `cart_value`, медиана и IQR `cart_item_count`;
  - диагностическая таблица соответствия версий и флага: строки — `app_version`; колонки — `Диапазон дат`, `N пользователей с cart`, `Доля redesign = 0`, `Доля redesign = 1`, `Смешанные сессии`; сортировка по версии и первой дате появления;
  - sensitivity checks — компактная таблица со строками `Основная user-level оценка`, `Session-level`, `Europe/Moscow`, `Без нарушенных последовательностей`, `Альтернативное присвоение смешанного флага`; колонки — `Δ cart → purchase`, `95% CI`, `Δ ключевого перехода`, `95% CI`, `Меняется ли вывод`.
- **Комментарий автору:**
  - недельный график не должен содержать отдельные линии по `app_version`: при малом числе наблюдений это создаст нечитаемый spaghetti chart;
  - высота общего figure около 560–640 px, общий X, спокойная сетка только по Y, прямые русские подписи осей и единиц; `displayModeBar: false`;
  - CI показывать error bars, а не непрозрачные широкие ленты, которые при малом числе точек доминируют над линией;
  - не проводить регрессионную линию по 2–3 post-релизным точкам и не называть визуальное направление статистическим трендом;
  - exposure-контраст показывать таблицей, а не bars рядом с календарным графиком: это другой способ формирования групп, который нельзя визуально выдавать за эквивалент pre/post;
  - совпадение направления двух контрастов повышает согласованность с гипотезой о проблеме редизайна, но не доказывает причинность из-за самоотбора в обновление и возможного смешения платформ;
  - расхождение контрастов должно быть явно вынесено в текст как основание проверить календарный фон, состав групп, версии и логирование;
  - отсутствие надёжного `platform` не позволяет использовать web как контроль и не позволяет отдельно проверить iOS против Android.
- **Переход дальше:** совместное чтение масштаба общей просадки, её локализации, сегментной неоднородности и устойчивости к альтернативным определениям позволяет сформулировать условное решение: откат, точечный фикс или продолжение наблюдения.

## Выводы

- Общий ответ на RQ должен начинаться с оценённого изменения `cart → purchase`, его 95% доверительного интервала и сопоставления с заранее заданным `δ_min`, а не с единичной точечной оценкой.
- Проблемный шаг можно назвать локализованным только если один переход даёт доминирующий вклад в общий спад, его ухудшение устойчиво после учёта неопределённости и не исчезает в sensitivity checks.
- Вывод об особенно сильной просадке среди новых или вернувшихся пользователей допустим только для сегментов, прошедших объёмный gate; результаты по `traffic_source` зависят от проверки стабильности этого поля внутри сессии.
- Разложение blended-изменения должно отделять ухудшение конверсии внутри сегментов от эффекта смены их долей; сам по себе изменившийся микс не подтверждает проблему checkout.
- Совпадающие календарный и exposure-контрасты, устойчивый недельный разрыв и стабильность результата при альтернативных расчётах согласуются с реальной проблемой редизайна, но не превращают pre/post-анализ в причинный эксперимент.
- Сравнить iOS, Android и web по доступной выгрузке нельзя: отдельного поля `platform` нет, а `app_version` и `is_checkout_redesign` не являются надёжной заменой платформе.

## Рекомендации

- **Если просадка превышает `δ_min`, локализована на одном переходе, сохраняется по неделям и согласуется с exposure-контрастом:** приоритизировать точечный фикс найденного шага; откат рассматривать при высоком сценарном бизнес-риске или невозможности быстро выпустить исправление.
- **Если ухудшение распределено по нескольким шагам или сопровождается аномалиями событий:** до продуктового решения провести аудит релиза и логирования; не сводить проблему к paywall только по наличию события `payment`.
- **Если общий эффект мал, CI включает отсутствие продуктово значимого изменения, а результаты sensitivity checks нестабильны:** продолжить наблюдение и накопить объём вместо немедленного отката.
- **Если основная часть blended-изменения объясняется миксом, а внутрисегментные конверсии стабильны:** проверить причины смены состава аудитории и не приписывать просадку редизайну.
- **Если новые пользователи действительно теряются сильнее:** направить UX- и техническую диагностику на ключевой переход для new-сегмента, сохраняя оговорку о недатированном `prior_purchase_count`.
- Для следующего измерения дособрать явные `platform` и `device_type`, надёжную дату/статус экспозиции к редизайну, события показа платёжного интерфейса, ошибок и отказов оплаты, а также флаги тестовых аккаунтов и ботов.
- Для причинного решения о редизайне использовать holdout, контролируемую раскатку или A/B-дизайн; web можно применять как сравнительный фон только после надёжной идентификации платформы и проверки сопоставимости трендов.

## Out of scope

- Сравнение iOS, Android и web: поля `platform` и `device_type` отсутствуют.
- Причинный вывод о влиянии редизайна: нет рандомизации, holdout или надёжной контрольной группы.
- Диагностика конкретных ошибок оплаты, paywall и UX-причин отказа: в данных есть только агрегирующее событие `payment`.
- Анализ способов оплаты, банков, географии, продавцов, категорий товаров и промокодов: соответствующих полей нет.
- Расчёт фактически потерянной выручки или маржи: `cart_value` позволяет только сценарный sizing, но не заменяет данные о заказах, оплате, возвратах и марже.
- Кросс-девайсная воронка: отсутствует подтверждённая identity-склейка между платформами.
- Детальное ранжирование малых сегментов и источников трафика: ячейки ниже объёмного gate не используются для продуктовых выводов.
- Дневные тренды, многочисленные линии по версиям, декоративные funnel chart, pie/donut и KPI-витрина: они не усиливают ответ на центральный вопрос при доступном объёме данных.
